# pdfcraft-platform

Layer L7 holds operating-system services that both the desktop app (`pdfcraft-ui-egui`) and the automation tools (`pdfcraft-automation`) need. Those two crates sit on the same layer and can't depend on each other, so a helper they share lives here instead of being copied into each (`xtask/src/layers.rs` allows both edges). It has no UI dependencies; macOS filesystem calls use the safe `rustix` wrapper.

`staging` creates the temporary file an atomic save writes before renaming it over the target. The file is opened with `create_new`, so anything already at the name (a file, a hard link, a symbolic link even when dangling, a folder) is skipped and never written through. On Windows a folder at the name fails with "access denied" rather than "already exists", and is skipped only when something is actually there. Names carry an unpredictable 64-bit suffix from `staging_suffixes` (the standard library's keyed hash, currently SipHash-1-3, keyed from the operating system's random source), which stops a name being planted in advance but is not a CSPRNG; fixed suffixes are only for tests. At most 16 names are tried, and then the save is refused. The target's name is cut to 128 bytes on a character boundary so the staging name fits every system's limit. Each caller keeps its own name form (`.{name}.{suffix}.pdfcraft-tmp` for automation, `.{name}.pdfcraft-{suffix}.tmp` for the desktop save). Writing, closing the file before the rename, renaming and removing the staging file on failure stay with the caller.

Synthetic tests pin both name forms, the 128-byte cut, the attempt limit and refusal when no name is left. The planted-file, link, folder and failed-rename tests stay with each caller, where they exercise the whole save.

On macOS, `write_atomically_with` copies the existing regular destination's accessible extended attributes to the open staging file after writing the data and before flushing and renaming. Finder tags, comments, binary values and empty attributes therefore survive both incremental and full saves (#2658). Save As retains attributes of an existing destination; a new destination does not inherit metadata from the source PDF. Missing files and filesystems without xattr support keep working. The metadata read does not follow the destination's symlink or block on a FIFO. macOS manages the new file's `com.apple.provenance`; it is not copied. Kernel-hidden compression attributes are not requested.

Attribute copying is bounded: 64 KiB of names, 1024 attributes, 16 MiB per value and 64 MiB total. Each value must fill the initially queried size and retain that size in a second query after reading: a resource fork may return a partial prefix on growth rather than an error. A read/copy error or exceeded bound returns an error suggesting Save As; the original bytes and metadata stay intact and the staging file is removed. Flush errors retain the same guarantee. Tests cover exact metadata before flush and after repeated saves, empty/binary values, oversized resource forks, a simulated partial read of a growing fork and symlink isolation. Automation covers incremental/full saves, Save As and retaining an unsaved edit after metadata refusal. The staging writer also retains Unix permissions, the Windows hidden and system attributes (the staging file is created with them, so a hidden file is never published visible and a plain one never hidden, #4593) and, where supported, Windows/macOS creation dates; attribute copying runs before the creation date is restored. ACLs and hard-link identity are not preserved.

`assistant` holds the AI assistant's OS services (M13.A7). Nothing in it runs unless the user turns the assistant on and asks a question.

`HttpsTransport` implements `pdfcraft_ai::transport::Transport` with `ureq` 3, using the same version, features and OS certificate verifier that craft-update already builds, so nothing new enters the tree.
- **Policy.** It applies `check_url` before connecting (HTTPS anywhere, plain HTTP only to this computer) and follows no redirects: a 3xx is refused, so the key and the document are never sent to another address.
- **Proxies.** A loopback address (a local model) is reached directly, never through a proxy from the environment.
- **Limits.** Connect, first-byte and whole-answer timeouts apply. The answer is capped at 16 MiB decoded, counted after gzip, and the caller can cancel between 16 KiB pieces.
- **Tests.** A one-shot loopback HTTP server covers a streamed answer with the request as sent, an error status with its body, a refused redirect, the cap, cancellation, a refused address and a closed port.

`Keychain` keeps the API key in the macOS login keychain, as a generic password named "PdfCraft AI assistant". Other systems answer `Unavailable` for now.

`SessionKeys` keeps keys in memory only, for portable mode and systems without a keychain.

`ClaudeCode` is the other way to Claude: it runs the user's own `claude` program for each request, signed in with their Claude subscription (personal use; the rules are in `pdfcraft_ai::claude_code`).
- **Finding it.** `PDFCRAFT_CLAUDE`, `~/.local/bin`, `~/.claude/local`, Homebrew, `/usr/local/bin`, the `PATH`, then the copy inside the Claude desktop app. Finding it only looks at files; nothing runs until the user chooses Claude Code and asks.
- **Locked down.** No tools, MCP servers, hooks, plugins, CLAUDE.md, memory or saved session; it runs in an empty folder of its own, and `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_OAUTH_TOKEN` are taken out of its environment so the subscription is used.
- **Limits.** 16 MiB of output, 4 MiB per line, stopped after 3 minutes without output or 15 in all, or when the user stops it; the program is killed when a run ends early.
- **Sign-in.** `sign_in()` asks the program (`claude auth status`); PdfCraft never reads its credentials.
- **Tests.** A fake `claude` (a shell script) covers an answer with its citation and the arguments it got, bad arguments, a missing program, a silent one, a flood, the sign-in check, finding it, and the environment it gets.

`api_key(store, account, env)` looks for a key in this order: the stored key, else `ANTHROPIC_API_KEY`, each checked as printable ASCII of at most 1 KiB. The key is never written to a settings file. The real keychain round trip is an `#[ignore]` test (`cargo test -p pdfcraft-platform -- --ignored`), since it changes the user's keychain.

`drive` finds Google Drive for desktop's folders, so the app can open and save in them (File ▸ Open from Google Drive…, File ▸ Save to Google Drive…, the Google Drive panel); Drive uploads what is saved there. PdfCraft never talks to Google: no sign-in, no network code. A PDF opened from Drive is an ordinary file, so saving it writes the synced copy.
- **Where.** On macOS, one folder per account, `~/Library/CloudStorage/GoogleDrive-<account>`, holding the account's places (My Drive, Shared drives, Other computers), named in the system's language; `my_drive` knows the common names. On Windows, a drive letter holding a My Drive folder (not yet tried on a Windows machine). Linux has no Drive for desktop. `place` says which account a path is in and the folders from its place down.
- **Listing.** `entries` gives a folder's folders, then its PDFs (size and time changed), each by name, without hidden ones; `folders` only the folders. An online-only PDF is listed like any other, and Drive downloads it when it is read.
- **Permission.** macOS asks the user before an app may read these folders. Until then listing fails with `ListError::NotAllowed`, and the app says how to allow it.
- **Bounded.** 50,000 entries read, and 5,000 folders and 5,000 PDFs listed per folder, 32 accounts. `check_name` refuses names that could leave the folder or break a synced copy (`/ \ : * ? " < > |`, control characters, `.`/`..`, a leading dot, a trailing dot or space, Windows device names, more than 255 bytes) before anything is made or renamed. `rename` keeps a PDF's `.pdf` and refuses a name already taken, except the file itself in another case.
- **Tests.** A home folder laid out as Drive keeps it covers accounts and places, listing (folders then PDFs, sorted, no other files or hidden ones, links followed), placing a path in its account, a folder that can't be read, names, a new folder made only inside the one chosen, and renaming (a PDF stays one, a taken name is refused, a change of case is not).
